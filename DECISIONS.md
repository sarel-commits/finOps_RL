# DECISIONS

1. **uv install location**: uv was not installed and Homebrew is absent. I installed uv via the official installer into ~/finops-eval/.tools/bin with UV_NO_MODIFY_PATH=1, so no shell profiles or system paths were touched (hard rule: nothing outside ~/finops-eval / no system changes).
2. **Quantization bits**: 64 GiB RAM >= 48 GB, so I used 8-bit (group size 64) as specified. The 4-bit fallback was not triggered.
3. **huggingface_hub[cli] extra**: hub 2.4.0 no longer defines a `cli` extra; the `hf` CLI ships in the base package. No action needed.
4. **Model download bandwidth**: the link measured ~34 Mbps (networkQuality), so the 55.6 GB BF16 download takes several hours. I kept downloading the BF16 repo as specified, since converting it myself is the preferred path, and built and debugged all harness code in parallel.
5. **ITBench-Lite subset**: I downloaded only `snapshots/finops/**` + README (14 MB) rather than the full dataset (multi-GB SRE snapshots not needed).
6. **Quantization/serving library**: both mlx-lm 0.32.2 (`mlx_lm/models/qwen3_5.py`) and mlx-vlm 0.7.12 (`mlx_vlm/models/qwen3_5`) support `qwen3_5`, so no upgrade was needed. I chose **mlx-lm** for both conversion and serving because `mlx_lm.server` (a) parses this model's XML tool-call format via its `qwen3_coder` tool parser (auto-inferred from the chat template), and (b) accepts `top_k`, `presence_penalty`, `seed` and `chat_template_kwargs` (needed for `enable_thinking`) per request. mlx-lm's qwen3_5 loader drops the vision tower, so **the converted model is text-only** (vision encoder not included). All benchmarks here are text-only, so this does not affect results.
7. **ITBench-Lite FinOps scoring**: the official evaluator (github.com/itbench-hub/ITBench-Evaluations, commit 14f026f, `--domain finops`) is an LLM-as-a-judge whose rubric (prompts/finops_main.py) is: score 1 iff *all* ground-truth root-cause resources are matched by `name` and `type`, else 0; aggregated as pass@1. Using an LLM judge would need either a paid API (forbidden) or the model judging itself (biased). I therefore implemented the rubric **deterministically** in scripts/score_itbench_lite.py: the agent output is `{"resource":[{"name","type"}]}`; name match = exact after trim (case-insensitive); type match = case-insensitive, whitespace/underscore-normalized ("Instance Family" == "instance_family"). Primary metric: `root_cause_resource` pass@1 (official rubric). I also report a secondary name-only match and precision/recall/F1 over predicted resources (to compare loosely with the paper's AD F1), clearly labeled.
8. **ITBench-Lite agent prompt**: no official agent-side FinOps prompt is published (ITBench-Evaluations has only judge prompts; the Kaggle page is JS-rendered and returned no content). I wrote a task prompt from the dataset card's task definition ("Identify the resource responsible for anomalous cost changes using synthetic cost anomaly details") and the documented output format (`{"resource":[{"name":..,"type":..}]}`, Kaggle example type "instance family"). The prompt is saved verbatim in each run's config.
9. **Agent design for ITBench-Lite**: each data.csv is ~870 KB / ~15k rows (~300k tokens), too large for the context window, so the agent gets a sandboxed `run_python` tool (pandas available, cwd = a scratch copy of the scenario containing ONLY anomaly.json and data.csv; ground_truth.yaml is never copied). Trajectories are scanned for references to "ground_truth" as a leakage check.
10. **Full ITBench FinOps scenarios (library scenarios 37/38)**: SKIPPED. They deploy OpenTelemetry-Demo onto a Kubernetes cluster via Ansible/helm/kubectl (kind/minikube locally need Docker or Podman). No container runtime, kubectl, helm, kind or minikube is installed, there is no Homebrew, and installing a container VM would mean system-level changes (hypervisor/VM, possibly privileged helpers), which the hard rules forbid. The cluster plus the 27B model would also contend for 64 GB unified memory. ITBench also publishes no FinOps leaderboard/evaluator for these live scenarios (only SRE/CISO leaderboards in the repo).
11. **Dev model**: briefly started downloading mlx-community/Qwen3.5-2B-4bit to debug the harness; the user asked to use only Qwen/Qwen3.8-27B, so it was removed (partial download deleted, never used). The harness is debugged directly against the Qwen3.8-27B 8-bit model.
12. **mxfp8 available but not used**: mlx-lm 0.32.2 `convert` offers `--q-mode mxfp8` (OCP microscaling FP8, E4M3 elements with a shared power-of-two scale per 32 values). The task explicitly says to use MLX *affine* 8-bit as the FP8 stand-in and not to attempt true FP8, so I used `--q-mode affine --q-bits 8 --q-group-size 64`. mxfp8 is listed in the report as a follow-up for a closer FP8 match.
13. **crc32.txt scope**: the repo crc32.txt lists only the 8 tokenizer/config files, not the weight shards. I verified those 8 by CRC32 and verified all 18 shards (plus other LFS files) against the Hub LFS SHA-256 and byte size (scripts/verify_download.py), a strictly stronger check.
